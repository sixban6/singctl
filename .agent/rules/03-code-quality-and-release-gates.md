# 规则 03：代码质量、权限安全与发布前门禁准则

## 1. 架构与安全编码红线

- **保持极简零外部依赖**：坚持单二进制内嵌静态资源架构，不引入 Docker、Redis、MySQL 等重型外部依赖，兼顾 512MB～1GB 小内存 VPS 与 OpenWrt 软路由。
- **敏感落盘强制 `0600`**：所有包含凭据、密钥、Token 或节点清单的持久化文件（`singctl.yaml`、`fleet.yaml`、`fleet_keys/*`、`config.json`、Token 文件）写入或原子替换时必须确保权限为 `0600`（目录 `0700`）。
- **防命令注入与防越权**：所有拼入远程 Shell 或系统命令的参数必须做严格白名单校验或 Base64 管道解码传递；服务端遥测端口（如 Clash API `9099`）与后台服务（`8092`、`3001`）仅允许绑定 `127.0.0.1` 回环地址。
- **遵循现代 Go 规范**：基于仓库 `go.mod` 目标版本使用标准库现代特性（`cmp.Or`、`slices`、`maps`、`strings.SplitSeq`、`atomic.Bool`、测试中使用 `t.Context()`）。
- **遵守开闭原则（OCP：对扩展开放，对修改关闭）**：
  - **稳定核心流程，横向扩展真实变化轴**：将核心编排主干（配置编译流水线、守护巡检调度、防火墙/沙盒编排、审计检测器、多平台服务托管）与易变策略解耦。对存在多变体或持续扩充的维度（协议、分流/防火墙规则层、诊断项、DNS 上游、平台适配），通过**新增独立的策略实现（消费侧小接口）、流水线阶段（Stage）或声明式规则表项**横向扩展，**禁止每次加需求都在既有核心大函数里拆改或堆砌超长 `switch` / `if-else`**；对无多态需求的单一纯函数保持直接简洁，不套空壳接口。
  - **契约演进向后闭合**：对已有函数签名、YAML/JSON 配置文件及 Web API 保持向后兼容（对破坏性修改关闭），通过带安全默认值的可选字段或 `Option` 模式平滑扩展；新增扩展点须在当前业务或测试中真实挂载，避免产生悬空死代码（契合 CI `deadcode` 门禁）。

## 2. 测试驱动开发（TDD：全流程先测后写）

Go 侧（`cmd/`、`internal/`、`test/`）全部代码研发（**新功能 `feat`、Bug 修复 `fix`、性能优化 `perf`、重构 `refactor` 100% 覆盖**）严格执行 **Red → Green → Refactor** 闭环：

- **先写完整测试并验证红灯（Red），再写实现（Green）**：
  - 开发任何新功能、新接口或修复缺陷前，必须**先仅编写测试代码**（新功能可先定义空函数签名骨架），并**实际运行 `go test` 确认按预期失败（Red）**，随后才允许编写业务实现使其全部转绿（Green），最后在绿灯保护下清理重构（Refactor）。严禁“先写完实现再补测试”或“同一轮同时写完测试与实现”的伪 TDD。
  - 重构（`refactor`）或性能优化（`perf`）若涉及缺少单测的老代码，必须先补齐锁定既有行为的完整基准测试并确认全绿，再动手改造。
- **前置穷举完整边界条件**：编写前置表驱动测试（Table-Driven Tests）时，必须一次性考虑并覆盖：
  1. 正常业务主路径；
  2. 空值、`nil`、零值、极值与超长/畸形输入；
  3. 非法格式、越权请求与命令/配置注入恶意载荷；
  4. 下游超时、失联重试退避与失败自动回滚；
  5. 重复调用幂等性及 `-race` 高并发读写竞争。
- **I/O 可测解耦与宿主机零污染**：涉及外部命令、网络、防火墙、时钟等副作用时，通过消费侧小接口或结构体字段注入测试替身（未注入 `nil` 时自动回退生产默认实现，严禁篡改包级全局变量）；所有单测落盘必须限制在 `t.TempDir()`，严禁读写宿主机真实 `/etc`、`/var`、内核防火墙或依赖外网。
- **前后端与文档边界**：涉及前后端 API 契约的改动须先写后端 `webui` / `serverweb` 契约单测；纯前端（`web/`）视觉/交互微调免于单测，由 `npx tsc --noEmit` 强类型检查与 `npm run build` 门禁兜底；纯文档（`docs/`、`.agent/`）与只读排障命令豁免。

## 3. 提交与发版前必跑验证门禁

每次修改代码准备提交前，必须本地实际运行并通过以下检查（不得跳过或伪造结果）：

1. **若修改了 `web/` 前端代码**：必须执行 `cd web && npx tsc --noEmit && npm run build`，将最新构建产物同步至 `internal/serverweb/static/` 与 `internal/webui/static/`。
2. **Go 静态检查、死代码检测与竞态测试**：必须执行并通过：
   ```bash
   go vet ./...
   go run golang.org/x/tools/cmd/deadcode@v0.53.0 -test ./...
   go test -race ./internal/...
   go test -short ./test/...
   ```
3. **注释与文档同步**：保留无关既有注释；若新增或变更 CLI 参数、配置字段（如 `knownYAMLKeys`），同步更新配置模板与 `docs/` 文档。

## 4. Git Commit 信息规范（强制）

每次执行 `git commit` 时，必须使用语义化前缀，并在标题与正文中清晰说明以下内容：

- **前缀约定**：`feat:`（功能新增）、`fix:`（bug修复）、`perf:`（性能优化）、`refactor:`（重构）、`docs:`（文档）、`chore:`（杂项）。注意 `.github/workflows/release.yml` 会对 `docs` / `style` / `test` / `ci` 前缀跳过自动发版。
- **变更类型**：在提交正文明确标出本次属于「功能新增」、「bug修复」还是「性能优化」（复合改动需逐一注明）。
- **改动原因**：用 1～2 句简短说明本次改动的起因或要解决的问题，再列出核心改动要点。
